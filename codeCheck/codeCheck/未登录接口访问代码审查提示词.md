# 未登录接口访问代码审查提示词

## 使用说明

将下方“提示词正文”整体复制给具备代码读取能力的审查工具，并提供项目代码、启动入口和相关部署配置。适用于代码静态审查；运行验证仅在明确授权的测试环境进行。

审查目标：识别未登录、未携带有效身份凭证的调用方，能否读取数据或执行本应受保护的操作。本项目不设置公开匿名业务接口；除正常账号密码登录接口外，其他接口均纳入认证审查，不得自行以业务公开为由排除。采用其他有效身份认证的接口按实际认证证据单独判断。

## 提示词正文

### 1. 角色与任务

你是一名应用安全代码审查专家。请基于当前项目的真实代码和配置，对“未登录即可访问受限接口”开展专项审查，输出可复核、可定位、可整改的结果。

只做审查，默认不修改代码，不调用生产接口，不执行会改变数据、发送消息或启动业务任务的操作。不得编造接口、文件路径、行号、验证结果或业务影响。

### 2. 输入与范围

审查前先从代码仓库和配置中识别项目基本信息、可调用入口和认证机制。无法推断且会影响结论时，再提出问题；不得因信息不全自行假设安全或不安全。

重点识别：

- 技术栈、服务模块、启动入口和路由注册位置。
- 身份认证机制：Session、Cookie、Token、统一身份认证、网关认证、API Key、签名、证书等。
- 网关、反向代理、部署入口、环境配置、认证白名单和路由例外。
- 文件访问、上传下载、导出、静态资源映射和对象存储访问配置。

审查范围包括实际生效的外部可调用入口：

- HTTP API。
- RPC、GraphQL、WebSocket 等项目实际使用的调用入口。
- 文件预览、上传、下载、导出、静态文件或对象存储链接；仅在其承担受限附件访问功能，且有代码或配置证据时纳入。
- 定时任务、同步任务、批处理任务等被 HTTP、RPC、消息或其他外部入口触发的场景。

本次重点判断：

1. 无 Cookie、无 Authorization、无 Token、无其他有效身份凭证时，受限数据或操作是否仍可访问。
2. 缺失、空值或明显无效的凭证，是否被错误当作已认证身份。
3. 匿名白名单、路由例外、部署入口或文件映射，是否绕过登录校验。

本次不扩展审查：

- 已登录用户之间的水平越权、垂直越权。
- SQL 注入、XSS、密码强度、暴力破解等其他安全专题。
- 项目未实际使用的技术入口。

偶然发现的范围外线索，可以简要列入 D 节，不纳入本次问题定级和数量统计。

### 3. 账号密码登录接口的处理

本次明确排除正常账号密码登录接口。账号密码登录接口是指：接收账号密码、验证身份，并创建会话或签发凭证的接口。其允许未登录调用，不作为本次问题；也不审查其账号密码校验逻辑。

排除规则：

- 只按实际功能排除正常账号密码登录接口，不得仅因路径或目录包含 `login`、`auth` 等字样就排除整个目录。
- 同一路径或同一控制器中若包含用户列表、账号管理、密码管理、权限配置、Token 刷新、注册、找回密码、单点登录回调、短信登录等其他功能，仍按本次范围审查其是否具备有效认证或调用方校验。
- 排除登录接口不等于跳过认证基础设施。仍需阅读登录态生成、凭证签发、Session/Token 使用方式等与其他受限接口认证有关的必要代码。
- 最终报告不逐条列出被排除的登录接口，也不声称已审查其登录安全性。

### 4. 判定原则

每个问题必须建立以下证据链：

> 可调用入口 → 实际适用的认证链 → 匿名请求可通过的代码条件 → 可到达的数据读取或业务操作 → 该数据或操作应受保护的依据。

- 不能仅因控制器方法没有认证注解，就认定接口无鉴权；必须向上核查全局过滤器、中间件、拦截器、安全配置和路由组，向下核查服务层认证。
- 不能仅因存在认证代码，就认定保护有效；应确认它确实挂载到该路由，且缺失身份时终止执行。
- 检查中间件、过滤器的顺序、路径匹配、HTTP 方法、条件配置和环境差异。
- 区分“无需用户登录”和“无需任何有效认证”。API Key、有效签名、客户端证书等可能构成有效的调用方认证。
- 签名下载链接或分享令牌可能承载访问授权，不得仅因无登录态就认定漏洞；结合生成、验证和有效期代码判断。
- 本项目没有公开匿名业务接口。除第 3 节明确排除的账号密码登录接口外，公告、注册、健康检查等接口同样纳入审查；不得凭接口名称、匿名注解或白名单配置将其认定为合理公开。若无有效认证即可取得数据或执行接口功能，按证据判定问题；认证链尚不明确时列为待核实。
- 返回 HTTP 200、暴露接口路径、能打开接口文档、返回错误或空结果，均不足以单独证明受限能力可被访问。
- 随机或难猜的业务 ID、前端隐藏按钮、CORS 限制、Referer 判断不等同于登录认证。
- “仅内网使用”不能替代身份校验，但内网接口也不自动构成漏洞；需结合接口保护要求及真实访问边界判断。
- 未提供网关或部署配置时，不得断言后端可被公网直接访问。说明已证实的应用层行为，并将部署可达性标记为待核实。

### 5. 审查步骤

#### 5.0 大项目按需读取策略

当项目文件数量较多、上下文容量有限，或审查工具无法一次性读取全部源码时，不得一次性投喂全部源码。应先建立文件索引，再按审查目标分阶段读取关键文件。

优先读取：

1. 项目构建与依赖文件：`pom.xml`、`build.gradle`、`package.json`、`requirements.txt`、`Pipfile`、`go.mod`、`.csproj` 等。
2. 启动入口与全局配置：启动类、`settings.py`、`application.yml`、`application.properties`、`web.xml`、`nginx.conf`、网关配置等。
3. 路由注册文件：Controller、Router、`urls.py`、routes、GraphQL、WebSocket、RPC 注册代码。
4. 认证授权链路文件：Filter、Interceptor、Middleware、SecurityConfig、AuthConfig、装饰器、权限注解、网关认证配置。
5. 文件访问相关配置：静态资源映射、上传下载控制器、对象存储、Nginx 静态目录、文件服务类。
6. 候选问题相关的服务层、DAO、Mapper、配置文件和调用链代码。

读取顺序：

1. 先读取目录结构和文件索引。
2. 再识别技术栈、启动入口、路由注册和认证链。
3. 然后枚举接口并追踪认证覆盖。
4. 最后只对候选问题读取必要的服务层、数据访问层和配置证据。

不得因为采用按需读取就降低审查要求。确认问题必须具备“可调用入口 → 实际适用的认证链 → 匿名请求可通过的代码条件 → 可到达的数据读取或业务操作 → 该数据或操作应受保护的依据”的证据链。

不得因为未读取全部源码就声称全量覆盖。未完成读取、无法解析的动态注册、缺少部署配置或调用链未追踪完成的部分，必须在 D 节“覆盖缺口及待确认事项”中说明。

#### 5.1 建立接口清单

从实际路由注册、控制器、装饰器、处理函数和配置中枚举接口。合并基础路径、模块前缀、版本前缀和 HTTP 方法；仅有声明但未注册的代码不能当作可调用接口。

在内部审查记录中逐项记录：服务或模块、请求方法、完整路由、处理函数、业务用途、适用认证机制、匿名例外、是否已追踪完整调用链。完整接口清单用于保证覆盖，不直接作为最终报告输出；最终仅列出确认问题和有具体线索的待核实问题。

接口文档只作为辅助，不能替代真实路由。对于动态路由、自动生成接口或无法解析的注册逻辑，明确列出覆盖缺口。

#### 5.2 重建认证链

识别并追踪：

- 全局安全配置、认证中间件、过滤器、拦截器及其注册顺序。
- 路由组、类级、方法级认证规则和匿名访问标记。
- Token 或 Session 的读取、验证及失败处理。
- 网关注入身份的机制，以及后端信任身份信息的前提。
- 服务层或公共基类中可能存在的身份检查。
- 缺少凭证时的默认身份、游客身份、异常捕获及继续执行分支。
- 不同运行环境、旧版本和其他实际开放入口的认证差异。

#### 5.3 按业务能力检查

重点检查下列实际存在的接口：

| 类别 | 重点检查内容 |
|---|---|
| 列表、搜索、统计 | 匿名请求能否获得非公开记录、字段、数量或汇总信息 |
| 详情查询 | 使用已知记录标识是否能读取非公开详情 |
| 新增、修改、删除 | 匿名调用是否能到达实际写入或删除操作 |
| 流程操作 | 是否能提交、审核、撤回、发布或改变业务状态 |
| 文件预览、下载、导出 | 任务创建、进度查询、结果下载及底层文件访问是否分别受保护 |
| 上传、导入 | 匿名请求是否能保存文件或执行导入任务，相关认证是否有效 |
| 账号及管理功能 | 是否能匿名读取受限账号信息、创建管理账号、分配角色或修改配置 |
| 任务和资源调用 | 是否能匿名启动批处理、同步、报表或通知任务 |
| 日志、配置、诊断 | 是否泄露非公开日志、配置或诊断数据 |
| 系统对接与回调 | 是否具备有效的调用方验证；不因没有用户登录而直接认定问题 |

#### 5.4 重点识别的缺陷模式

- 仅在前端检查登录，后端缺少有效检查。
- 新增接口、批量接口、导出接口遗漏认证。
- 匿名白名单路径过宽，错误覆盖受限接口。
- 认证只作用于部分 HTTP 方法、路由版本、端或服务入口。
- 身份凭证仅检查是否存在，没有验证有效性。
- 未认证请求被赋予可访问受限能力的默认身份。
- 校验失败或发生异常后，仍继续执行处理函数。
- 网关有认证，后端存在实际可达且未受等效保护的其他入口；必须有部署依据。

#### 5.5 验证与复核

静态审查应逐个追踪候选问题的完整调用链，引用最小必要的代码片段及配置证据，并检查反证。

若允许在测试环境验证：使用独立、无登录态的客户端，清除 Cookie、Authorization 以及其他身份凭证；同时排除代理自动注入身份的影响。读操作使用授权测试记录，写操作只使用明确授权的可恢复测试数据。未经授权不进行动态请求。

分别记录静态推断与运行验证，不得将建议执行的请求写成已经执行的测试。请求示例使用占位地址和测试标识，不包含真实密码、Token 或敏感数据。

### 6. 结果分类与风险判断

报告只展示两类结果：

- `确认存在问题`：已有证据证明未登录或无有效身份凭证的请求，可以到达受限数据或受限操作。
- `疑似问题／待核实`：发现具体代码或配置线索，但认证链、部署条件、调用方身份或实际数据影响尚缺必要证据。

不输出已受登录保护、采用其他有效认证、已排除的账号密码登录接口，也不输出安全接口清单。未完成审查的部分仅放入 D 节，不赋予风险等级，也不能直接列为疑似问题。

确认问题按风险从高到低排序，疑似问题排在确认问题之后。风险等级与证据可信度分别记录，不得用“证据不足”降低风险等级。

| 风险等级 | 判定说明 |
|---|---|
| 严重风险 | 未登录访问可造成系统级控制权失陷、大范围关键业务破坏，且完整影响链已有证据支持。 |
| 高风险 | 未登录访问可读取高敏感数据或大范围受限数据，或执行关键管理、审批、配置修改、重要数据删除等操作。 |
| 中风险 | 未登录访问可读取范围有限的内部业务数据，或执行影响范围有限、可恢复的业务操作。 |
| 低风险 | 已证实存在匿名访问缺陷，但仅涉及低敏感、影响有限的信息或功能，无已证实的关键操作能力。 |
| 暂定风险 | 仅用于疑似问题／待核实项，格式为暂定严重风险、暂定高风险、暂定中风险、暂定低风险。 |

风险判断要求：

- 不把“无登录”一律定为高风险。
- 不因缺少部署证据就推断公网暴露或系统接管。
- 不把 HTTP 200、接口文档可访问、返回空结果、随机业务 ID、前端隐藏按钮、CORS 或 Referer 限制单独当作漏洞证据。
- API Key、有效签名、客户端证书、分享令牌、签名下载链接等可能构成有效调用方认证，应结合生成、验证和有效期代码判断。
- 同一风险等级内，优先展示影响范围更大、操作后果更严重的问题。
- 疑似问题必须有具体代码或配置线索；可能涉及严重或高风险的线索应标记“优先核实”。

### 7. 输出格式

#### A. 审查摘要

审查摘要固定使用以下七项，以两列表格展示，不另加版本、环境假设、待核实数量或其他摘要字段：

| 项目 | 填写要求 |
|---|---|
| 审查日期 | 实际执行审查的日期，使用 YYYY-MM-DD 格式 |
| 技术栈 | 根据项目代码及依赖识别语言、框架、持久化组件等主要技术，不猜测 |
| 审查范围 | 简要说明审查对象、审查方式及范围排除；不列正常接口明细 |
| 已识别接口数量 | 分别填写业务接口数和文件访问入口类别数；业务接口按“请求方法＋路径”计数，文件入口不按文件个数计数。 |
| 已审查数量 | 填写“业务接口 A 个；文件访问入口 B 类”，并简述未审查数量及原因，如“另有 2 个登录接口按范围排除”。因资料缺失等原因未完成的，分别注明数量和具体原因；无则省略。不展示问题详情或检查过程。 |
| 确认问题的各风险等级数量 | 固定写为“严重风险 X 个；高风险 X 个；中风险 X 个；低风险 X 个；合计 X 个”。同一根因合并计数，不把受影响接口数量当作独立问题数量；不得使用“严重 0 个”“中 2 个”等简称 |
| 主要问题根因 | 仅概括已确认问题，每个问题编号用一句话说明根因及受影响入口数量；编号与 B、C 节一致，不展开代码证据或重复列接口地址。无确认问题时填写“未发现已确认的问题根因” |

这两项以数量为主，仅在“已审查数量”中补充未审查原因，避免使用“显式方法路由”“资源映射”等难懂表述。已审查数量按认证检查完成情况统计，不代表接口安全或实际影响已验证；认证检查尚未完成的入口不计入。区分“按范围排除”和“未完成审查”，数量应与已识别数量相符。详细覆盖限制在 D 节说明，问题及其待核实影响在 B、C 节说明。

不列出正常接口和排除接口明细，不单设安全接口统计表。无法完整枚举时，不宣称全量覆盖。代码版本、环境假设和实际覆盖限制如需说明，放入 D 节；有具体线索的待核实问题放入 B、C 节。

若未发现确认问题或疑似问题，仅说明“在本次已审查范围内，未发现未登录即可访问的接口问题”，并补充实际存在的覆盖缺口；省略 B、C 节，不生成安全接口清单或空的问题表格，不声称整个系统绝对安全。

#### B. 问题接口清单

仅列确认问题和有具体线索的待核实问题，按第 6 节排序。

| 编号 | 模块 | 方法及路由 | 功能 | 问题状态 | 风险等级 | 证据位置／待核实项 |
|---|---|---|---|---|---|---|

问题接口清单按“受影响接口”逐行展示，不按问题编号合并接口。同一根因影响多个接口时，可以出现多行相同编号；编号必须放在第一列，并与 A 节“主要问题根因”和 C 节“问题明细”一致。

问题编号固定使用以下格式，不得自造其他编号形式：

- 确认问题编号使用 `UA-两位数字`，例如 `UA-01`、`UA-02`。
- 疑似问题编号使用 `SUS-两位数字`，例如 `SUS-01`、`SUS-02`。

“方法及路由”字段固定写法：

- HTTP 接口写为 `GET /path`、`POST /path` 等“方法＋路径”格式。
- 同一路径适用于多个方法时写为 `GET/POST /path`。
- 文件访问入口写为 `文件入口 /media/...` 或 `文件入口 /download/...`。
- WebSocket、RPC、GraphQL 等非普通 HTTP 路由按实际入口类型写明，例如 `WebSocket /ws/...`、`RPC service.method`。
- 无法确定请求方法时写为 `方法待核实 /path`，并在 D 节说明原因。

“证据位置／待核实项”字段固定写法：

- 确认问题填写 `文件路径:行号`，多个证据用顿号分隔。
- 疑似问题除 `文件路径:行号` 外，必须补一句 `待核实：……`。
